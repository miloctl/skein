# Five-agent panel review of the synthesis draft (2026-07-24)

Condensed findings. Five reviewers, distinct lenses, all grounded in the
actual codebase. Full reasoning folded into the final synthesis + PLAN.md.

## 1. Product sequencing (Product Manager lens)

- **Sequence by the transition date, not by architecture.** The manager layer
  needs exactly one thing from Phase 1 (`spawned_by` for finding→task); the
  rest of Phase 1's payoffs (thread view, efficacy analytics, auto-quiet)
  only open after team adoption (~month 3). Building them first burns the
  scarcest resource — pre-transition weeks.
- Recommended pre-transition order: manager layer → attention → finding
  dispositions → **meeting ingestion (promoted from P6 — "the worst slotting
  in the plan")** → metrics instrumentation.
- **Auth is not an open question**: private evaluative notes behind a
  spoofable X-User header must be fixed before any teammate touches the
  instance; discovery would destroy exactly the trust gradual adoption
  protects.
- Cut: skills/growth (needs input from a team that hasn't seen the tool),
  thread view, batch-approve/diffs from P3 (no volume yet), `supersedes` link.
- Metrics audit: 4 of 8 named metrics are not computable from planned data
  (reversal rate needs a `reverts` signal; review burden needs `claim_at` on
  the CAS claim; time-to-ownership and decision latency need proxies or
  should be dropped).
- P2's data-fed features must degrade to empty (no team data exists on
  day 1); every post-transition build should itself run as a timeboxed
  experiment (dogfood Phase 4's entity as the player-coach guardrail).

## 2. Scope skeptic (Minimal Change lens)

- "The synthesis kept sol's *mechanisms* with fable's *feature names*; it
  should have kept fable's mechanisms and dropped sol's tables."
- **`entity_links` → two plain columns** (`waiting_on`, `source_finding_id`).
  `answers`/`supersedes` already exist as dedicated columns; the unified
  table is a third representation of solved problems. Kill the legality
  registry and thread view. Generalize when a 4th relationship has a
  real consumer.
- **Shadow mode → nothing: the review queue IS shadow mode** (zero-risk
  proposals + approve/reject grading + trust scores already exist). Shadow
  pays only when volume overwhelms reviewers; with 2 agents it's a second
  queue to grade.
- Kill: trust profile evidence partitions ("clearest enterprise cosplay"),
  attention budget/ack machinery, auto-quiet control loop, structured
  rejection taxonomy (producer = consumer = same person), token budget
  config, coordination-debt composite, stakeholder signed pages, risk
  register as a feature (a risk IS a decision with review_by).
- Shrink: 1:1 workspace → one private note per person + query-powered brief;
  outcome contract → one markdown column; attention → 30 lines of grouping
  in the existing brief; authority half-life → one findings rule.
- **Privacy by structure, not by filter**: a separate table nothing joins —
  excluded from FTS/packs/digests because no code path touches it — converts
  a permanent filtering invariant into a one-time structural decision.
- Minimal pre-transition list (~2 weeks): private notes + brief, `fb:`
  prefix, meeting ingestion, commitment `audience`, onboarding playbook,
  review diff view, experiment kind + close conclusions, ICS as treat.

## 3. Architecture & data model (Software Architect lens)

- `entity_links` is defensible for narrative links but **drop `supersedes`**
  (decisions already have first-class CAS supersession the stale sweep and
  context pack read); SQLite can't enforce polymorphic FKs → write-time
  target validation + dangling-link sweep needed; index both directions.
- **`finding_dispositions` is keyed on the wrong identity**: findings re-fire
  weekly as new rows (`UNIQUE(rule_id, subject, week)`), so suppression must
  be evaluated inside `run_findings` against `(rule_id, subject)` disposition
  history; `digest_findings` must exclude dispositioned findings.
- **Shadow is five changes, not an enum tweak**: `agent_authority` CHECK
  requires a table rebuild; the gate branch must run *before* the global
  `AGENT_REVIEW` bypass; shadow writes return no IDs so agents can't chain —
  only single-shot writes are gradeable.
- Authority half-life = pattern reuse, not code reuse (new sweep, new column,
  new job — all small).
- Attention "no new table" is false if acks are kept (need
  `attention_acks(user, dedupe_key, acked_at)`).
- **15 leak paths for private records, not 5** — including digest→save_note→
  FTS laundering, unguarded `/api/admin/export` (any user, today), activity
  free-text details, `remember()` → every user's system prompt, thread
  traversal walking into private records, and the `fb:` prefix currently
  falling through capture to a team-visible indexed note.
- Plan-internal contradiction: stakeholder pages are beyond-LAN by definition
  while the plan defers all beyond-LAN auth.

## 4. Security & privacy (Security Engineer lens)

- **Header auth verdict**: solo = acceptable; team-of-6 = NOT acceptable for
  the feedback journal (the confidentiality target is evaluative content
  about the exact people who can spoof the header; detection ≈ zero);
  remote/multi-team = OIDC hard prerequisite.
- **The proportionate fix already exists in the repo**: personal hashed
  `sk-strands-` API keys. Rule: any private-record read/write requires
  key-resolved identity; X-User identity → 403. Days of work, not OIDC.
- **Two-tier storage**: visibility column + chokepoint enforcement suffices
  for participant-scoped data, but NOT for the author-private journal —
  backups (whole-file, mirrored off-box), export, and in-process MCP
  (identity = self-set env var) are file-level paths no column check stops.
  **Journal goes in a separate `private.db`** never opened by backup, export,
  MCP, or agent code.
- The write-time insight: exclusion machinery must exist **before the first
  private row is written** — FTS/backups/memories are write-time sinks;
  data written under weak discipline is already replicated by the time the
  team arrives.
- Nudge: read-time computation on the author's journal page ONLY. No
  notification row, no Slack (shared webhook broadcasts who's being
  journaled), no stored counters (one query away from a coverage dashboard).
- Refuse outright: exposing the current app beyond the LAN in any form; any
  agent/LLM path over the journal (memory injection + FTS + OTEL = four
  sinks from one touch); stored journal aggregation or embeddings; sol's
  "employee private prep" sections (don't collect what you can't protect).
- Meeting ingestion: proposals-only design neutralizes transcript prompt
  injection, but `fb:`-prefixed lines in transcripts must be flagged and
  skipped, never routed.
- Stakeholder pages: if ever, invert to push-generated static artifacts on a
  separate host; ICS = tokenized, LAN-only, team-visible data only.

## 5. Implementation feasibility (calibrated against this codebase)

- Sizes as drafted: P1≈2, P2≈3.5, P3≈2, P4≈1.5, P5≈3, P6≈3.5 EngDays
  (1 EngDay = the ~830-line backlog burn-down session). ~15–16 days as
  drafted; ~12–13 after cuts. P2 is the phase that can't slip and the
  biggest — pull its privacy foundation forward.
- Hand-waved items needing real specs: thread view (16-type entity resolver,
  cycle-safe traversal, naming collision with chat's `thread.tsx`); signed
  status pages (entire auth model missing); golden-trace evals (MockAgent is
  a hardcoded router — needs a scriptable scenario provider, ~1 day by
  itself); trust partitions (no `model_id` on `pending_changes`); charter
  surfacing (decisions have no category column).
- **Collisions**: `approve_change` compound-apply predates `db.transaction()`
  — wrap it before adding compound entities (removes a failure class);
  `fb:` must short-circuit in `capture()` *before* classification and refuse
  non-human origin; close-requires-conclusion breaks existing tests/seeds —
  backfill `unmeasured` and gate new closes only; attention must be a
  refactor of `briefing.py`, not a sibling service.
- Positive collision: the new jobs registry means every new sweep is one
  JobSpec and gets `/health` + `job_stale` coverage for free — mandate it.
- Batch approve is a hard prerequisite for meeting ingestion (per-line
  proposals flood the queue); rejection taxonomy is one column, cheap.

## Panel consensus (4+ of 5 agree)

1. Re-anchor everything to the transition date; manager layer + meeting
   ingestion pre-transition; analytics/UI layers post-adoption.
2. Private records require key-based auth from the first row; journal in a
   separate DB file; canary CI test over all egress surfaces.
3. Cut for now: shadow mode, entity_links generalization, thread view,
   attention budget machinery, trust partitions, stakeholder signed pages,
   auto-quiet.
4. Keep, shrunk: finding dispositions keyed (rule_id, subject); 1:1 = private
   notes + deterministic brief; outcome = one column + close-conclusion enum;
   attention = regrouped existing brief with reasons.
5. Experiments (kind/timebox/conclusion) are load-bearing for an ML team and
   cheap — ship pre-transition.
