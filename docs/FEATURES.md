# Skein — feature reference

Everything shipped, grouped by area. Every feature has a deterministic,
keyless core. Rows marked **LLM-upgradable** improve with a model provider but
do not require one. Human REST and agent tools call `backend/app/services/`.
Service writes carry `origin` and `created_by`, and they emit activity entries.

## Workplace extension contracts

Skein can compose an explicit allowlist of trusted workplace modules through
`create_app(settings, modules)`. The default `app.main:app` remains compatible.
Separate typed contracts cover routes, jobs, policy, identity mapping, service
identities, agent context, governed tools, specialists, events,
extension-owned migrations, and workflow actions. There is no universal plugin
base class and no automatic package scanning. There is no startup or shutdown
hook: a bare lifecycle callback would run trusted code with no declared
identity, policy action, or timeout, so private setup happens lazily from a
route, job, subscriber, or migration.

Authenticated core REST mutations, agent tools, classified MCP tools,
workflow steps, contributed routes, and frontend capability checks use the
composed policy boundary. A workplace permit cannot override a core denial.

Public task commands preserve the existing service write path, provenance,
and activity chain. That shared path writes versioned domain events to a
durable database outbox for human, agent, and integration callers.
Extensions receive typed views and safe events, not core rows.

The reference adapter bounds and validates remote responses. It classifies
temporary and unusable responses separately. Its status outbox uses per-item
ordering, leases, retry delays, dead-letter rows, and a wall-clock drain limit.
Task events use the same queue.

The frontend composes trusted packages before `next build`. Version 1 supports
policy-aware navigation and manager dashboard cards. `@miloctl/skein-frontend-host`
builds the installed host and explicit workplace packages without a source
checkout. The fictional Atlas project consumes `skein-agents`, the host, and
the extension API from exact local artifacts. It owns both dependency locks,
its PostgreSQL schema, final images, content, and deployment. See
`docs/EXTENSIONS.md`.

The template includes a consumer-owned unpublished contract. It accepts current
Skein source or one prebuilt artifact set. It reuses exact package bytes through
locks, installed-package tests, final images, an isolated PostgreSQL role,
readiness checks, signed OIDC, and a clean browser walk.

**Navigation (since 2026-07-26):** five top-level destinations — My Day ·
Chat · **Work** (Plan the week `/planning` · Health `/portfolio` · Browse
`/dashboard` · Insights `/insights` · Reports `/artifacts`) · **Inbox**
(Approvals `/review` · Requests `/intake` · Paste
notes `/ingest`) · **Team** (Agents `/agents` · 1:1s `/people` · Charter
`/charter` · Activity `/activity`). All URLs are unchanged; the groups are
tabs. Below the `sm` breakpoint the header gives its width to the search
field: the identity chip shows the avatar alone and carries the name as
screen-reader text, and the section tabs wrap. At 360px the row holds 328px
of content box, and the four things in it (logo, search field, identity chip,
capture button) do not all fit at their desktop sizes — the name at 7rem left
the search field 10px wide. `e2e/responsive.spec.ts` walks every page at
360px and fails on any sideways overflow. Manager-grade
controls (request triage, exec readout, authority editing, promise
verdicts) sit behind a per-browser **Management view** toggle so teammates do
not carry the management cockpit by default. The toggle shows its On or Off
state in visible text. It controls scope, not authorization: the endpoints
behind it are ordinary `CurrentUser` writes and stay reachable by anyone who
can reach the API — only authority editing requires an administrator
(AdminUser). Each route sets a distinct browser title. Chat keeps the current
thread title, and the attention count composes with both forms.

## Work tracking

| Feature | How | Surface |
|---|---|---|
| Milestones & tasks | statuses, priorities, due dates, assignees. A task takes `void` — the terminal state for one that never should have existed: it leaves every list, metric, commitment line and search result, stays readable at its own address, and a live status restores it (a confirmed control in the task panel; refused while delegated — the sponsor ends the delegation first). `done` could not carry this meaning, because done feeds throughput, cycle time and kept-%. `GET /api/tasks?status=open` and `?status=done&order=completed` apply state and order before the 500-row limit, then scan past workplace-policy denials. Browse carries create forms for milestones and calendar events and a confirmed delete for events — before those, the cards sent the reader to Chat, where the default mock provider has no milestone or event grammar. Browse reads both independently bounded slices from one `GET /api/tasks/browse` snapshot, so completed history cannot hide open work and a concurrent state change cannot split one task across snapshots | `GET/POST/PATCH /api/milestones`, `/api/tasks` · dashboard · tools |
| Questions & answers | assignment + notification to assignee | `/api/questions`, `/api/questions/{id}/answer` |
| Decisions with half-life | `review_by` date; daily sweep flips overdue ones to `stale`; supersede chains (`superseded_by`) instead of contradicting; reconfirm to reset; `category=charter` marks team-charter/decision-rights entries (review_by required, category survives supersession). A **risk register** needs no new feature: a risk IS a decision (`risk: <what> — mitigation: <how>`) with an owner and a `review_by`, riding the same stale sweep | `POST /api/decisions` (accepts `review_by`, `category`), `/api/decisions/{id}/supersede`, `/{id}/reconfirm`, `GET /api/decisions?status=&category=` · `/charter` page |
| Waiting-on edges | a task records what it's stuck behind (`waiting_on: task:12 \| blocker:3 \| promise:7 \| question:5`, `-` clears) — surfaced as health receipts and slip-forecast annotations; satisfied targets (done/resolved/kept) stop counting automatically. Deliberately not Gantt. **The edge reads BOTH ways**: the task peek names what finishing this one releases, `skein pr-body` puts that list in the pull request, and Work → Plan the week names the open task that releases the most. ONE edge counts as released work: a task waiting on this task. A `blocker:` edge deliberately does not, because `blockers.task_id` names the task a blocker BLOCKS rather than one that causes it — counting through it claimed a task released work while the same blocker was what stopped that task from finishing. A `promise:` edge is settled by a promise verdict, never by finishing a task, and a `question:` edge by the answer (`status = answered`) — a task stuck behind an open question now reads as waiting instead of idle. The walk is viewer-scoped at every hop (a task nobody may read is not countable through the chain), closes cycles on a visited set, and stops at ten hops and says so rather than reporting a number that quietly stopped counting. Until this existed, typing an edge cost the person who typed it and paid them nothing, which is how edges rot | `PATCH /api/tasks/{id}` · agent tool `update_task` |
| `/ask` with receipts | the nav box's `?` prefix. NOT a model call: the same FTS index, retried on the separate words when the phrase matches nothing, returned as snippets citing `entity #id` and marked as loose. Function words are dropped from the retry, or `the` alone matches most rows. Hybrid with semantic hits when embeddings are on | `GET /api/ask?q=` |
| Growth interests | self-declared per person (🌱 on My Day); shown in what-if staffing projections so growth fit is visible when staffing — display-only, no matching, no scores; overwrites logged old→new | `GET/POST /api/users/growth-interests` (prefilled; empty save clears) |
| Standups | blocker text auto-files a real blocker | `POST /api/standups` · CLI `skein standup` |
| @mentions | `@name` in a task (title or description), note, question, answer, or decision notifies the named person (immediate tier) — deterministic parse against the roster at write time, in the service layer, so every write path carries it with no new tool or gate row; `mention_log` dedupes by (entity, id, person), so an edit or typo fix never notifies twice; self-mentions and the question assignee (already pinged by assignment) are skipped; a name with a space cannot be one `@token` and is not mentionable. Agents are mentionable ON PURPOSE — an agent identity reads its notifications through `my_agent_inbox`, so `@scout take this one` reaches scout the way it reaches a person. **In a private shared chat**, a human mention notifies only a current human participant and links to the exact stored message. A removed member cannot read the old notification. In solo chat, a mention is delivered only by a row the turn files: an owner-scoped thread has no shared message row for a teammate to open. A turn that files nothing and names a teammate says who it did not reach and how to reach them (`turn_guard.unnotified` — deterministic, roster lookup, no model), and the Chief of Staff is told to route an `@name` into an `ask_question` or `create_task` carrying that name, asking first because "I spoke to @mira yesterday" is not a request. Keyless, `MockAgent` captures the message, so the note carries the name and the mention lands for real | `services/mentions.py` · rides the prose write paths |
| **Task side peek** | `?task=<id>` opens a panel over whatever page the reader is on — the one landing place for every task reference (My Day tasks and due-soon, Browse, Recently shipped, search hits, planning carryover). Shows status, priority, assignee, due date, the finish date once it is done, week, milestone, engagement, waiting-on, **the open blockers filed against it** (owner, impact, escalation — a blocker is what SETS status `blocked`, so a panel showing the state without naming its cause sent the reader to the register by hand), what finishing it unblocks, delegation, visibility, the forge link, and the worklog; delegation is a control inside it, and so is editing — status, priority, assignee, due date and waiting-on save from the panel (only the changed fields travel), with a one-click mark done; a DELEGATED task keeps status and done off the form, because the sponsor's verdict is the only path that ends a delegation. The panel also shows the durable delegation wake state and refreshes while the wake is pending or running. After a completed turn, the guidance leads with the task outcome: acceptance waiting in Inbox, a blocker, recorded progress, or no recorded progress. New human delegations queue one automatic bounded turn when background jobs are enabled. Legacy delegations, paused automation, refusals, and faults keep the editable `/as <agent>` Chat fallback when the provider can run it. Back closes it (a real history entry, not private state); Escape closes it; the background is `inert` while it is open, because `aria-modal` prunes the screen reader buffer and leaves Tab order alone. The joined milestone and engagement names take their OWN scope filters on the nullable side of the join, so a private parent's title never rides a readable task | `components/task-peek.tsx` · `GET /api/tasks/{id}` |
| **Row-level deep links** | Every link that names one row lands ON that row. `#question-12`, `#blocker-4`, `#milestone-9`, `#lesson-3`, `#promise-7`, `#charter-entry-5` — My Day's attention rows, the manager intervention queue, the since-you-looked brief, @mention and assignment notices, and receipt references all carry the id. Before this they named the SECTION (`#questions`, `#blockers`, `#promises`) and no element ever carried those ids, so the reader arrived at the top of a thirteen-section page holding a number to hunt for; question notices were worse and pointed back at My Day itself. The rows arrive from a fetch, so the browser's own fragment scroll fires before they exist — `lib/hash-target.ts` focuses the target once the data settles, and again on `hashchange` and on the `skein-hash` event an in-app link announces (a next/link soft navigation fires neither of the browser's). It focuses rather than scrolls, so a screen reader announces the row, and it lands ONCE per fragment — a background refresh must not pull the reader out of the control they moved to | `lib/hash-target.ts` · `lib/entity-ref.ts` · `services/briefing.py` |
| **Nav search + ask** | Below `sm`, the results panel uses viewport gutters instead of the narrow input as its anchor, so every result stays inside a 360px screen. A non-empty query shows **Enter**, and the input uses the native search enter-key hint on mobile. | Calendar | events, today's shown in My Day | `/api/events` |

| My Day briefing | attention items grouped by judgment type (Decide/Unblock/Promise/Review/Notice), each with a "why you're seeing this" reason. | Authority half-life | `autonomous` and `notify` grants receive a 90-day review date. After that date, the configured level remains on the audit row, but its effective level becomes `review`. A sponsor's task delegation remains task-specific authority for claim and progress, while `forbidden` still stops that loop. | Crews | Durable named groups of people, the membership the visibility tier reads (`docs/VISIBILITY.md`) — removing someone takes away their access to every crew-tier row they did not write. Whoever creates a crew becomes its **steward** — the person who adds and removes members — and a crew can never reach zero stewards from either side (removal and self-demotion both refuse). Editing needs strong identity plus stewardship of that crew, or an administrator named in `SKEIN_ADMINS`. Not the scarcity fallback that makes every key holder an administrator in a default trusted-header deployment — with it, any of them made themselves steward and evicted the one who was there, on a boundary that is about to decide what a person reads. An agent identity cannot join: agents read through the gated tool surface with its own authority matrix. Names fold in Python the way roster names do, so `Café` and `CAFÉ` are one crew, and the four system-actor names are refused. A crew is **deactivated**, never deleted (the roster's word, for the roster's reversible shape) — `crews_of` keeps returning a deactivated crew so rows already scoped to it stay readable, while `assert_writable` refuses new ones. Removal takes the person in the body, not the path: a roster name can hold `/`, which no URL path segment matches | `/settings` Crews card · `GET/POST /api/crews` · `POST /api/crews/{id}/members` · `services/crews.py` |
| Visibility tiers | Every content row carries `private` / `crew` / `workspace` (the baseline, 16 tables). `workspace` is the default and is exactly how every row behaved before the column landed, so the migration changes nothing anyone can see. **`crew` is filtered at read time** — `services/scope.py::visible_filter` returns an AND fragment spliced into each scoped read, and it takes the TABLE, never a column, because four tables carry both their real author column and a `created_by` holding the agent slug (on that one, a private note hides from the person who wrote it). **`private` is not filtered, it is excluded** — no FTS row, no embedding, no context pack, digest, readout, finding, calendar event, admin export row, and no body in `activity.detail` (`scope.detail`, because the ledger is hash-chained and a body written there has no undo). Jobs and egress builders have no viewer — "who is this digest for" has no answer — so they read `scope.WORKSPACE_ONLY` and nothing else. The handoff is generated by a person, so it takes a viewer and narrows the body to the artifact's own tier (`scope.audience`). Reading a scoped row needs STRONG identity: in trusted-header mode a name is whatever the caller typed, so `Viewer` carries the strength in the type rather than leaving the rule at every call site. A refusal is 404, never 403, and the absent row and the unreadable row raise the same sentence (`scope.missing`) — any other wording answers "does #12 exist" for sequential integer ids. Writing a scoped row needs crew membership, checked inside the write's own transaction. Handing one to somebody who cannot read it is refused at the write (`assert_readable_by`, with the author exempted — without that, every private capture that classified as a blocker was refused). Changing one you cannot read is a 404 (`assert_editable`, which lets a machine actor work a crew row because the forge webhook and the review-apply path ARE the mechanism, but never a private one). `scope.UNSCOPED` gives every unscoped table a written reason (pinned by `test_every_unscoped_reason_is_written`) and `scope.CLASSIFIED` maps every scoped one to its author column, and three CI tests walk the catalog and the service AST: any table in neither map, any id-addressed mutation with no guard, and any read of a scoped table with no viewer, no `WORKSPACE_ONLY` and no written excuse | Capture palette · standup card · `VisibilityPicker`/`VisibilityBadge` · `services/scope.py` · `tests/test_visibility_{writes,authz}.py` |
| Per-crew context packs | The team pack plus one section of that crew's own rows — decisions, conventions, open questions, open work. The shared body stays a prefix, so a reader can tell which half the whole roster has. Each crew versions independently (a shared counter would bump every crew whenever any one published), and the crew id is in the artifact filename as well as the row. Reading and publishing both need membership, resolved from the viewer so a self-asserted name is not a door; publishing also needs the crew to be active. API-only, on purpose: no page, CLI flag or job publishes a crew pack — the team pack covers the demonstrated need, and the surface stays dormant until a crew asks for one (docs/ROADMAP.md, cut table) | `GET /api/context-pack?crew=` · `POST /api/context-pack/publish` · `services/context_pack.py` |
| Identity walls | One name, one identity, asked the same way everywhere. `services/users.py::is_agent` folds in PYTHON (NFKC, strip category Cf, casefold) — no SQL collation reproduces that, so a SQL-folded wall and `resolve_teammate` would disagree about what one name is. Agent identities are refused on REST at every door AND at the perimeter, because the perimeter runs before any handler and the file-backed catalog reads never reach `routes/deps.py` at all. The four system-actor names (`system`, `scheduler`, `team`, `forge`) are refused for every kind, at creation, at rename, and at each credential door: the activity feed shows a system actor's rows to EVERY viewer, so holding one walks your own writes past the anti-surveillance rule. `refuse_fold_collision` refuses ANY row that folds onto an existing name, same kind included, so `Scout` the human never lands beside `scout` the agent and a second `SCOUT` agent never lands beside the first — authority and trust key on the exact name, so a fold-variant agent row answers to nobody's kill switch. A roster row that predates a wall is named in the boot log, never auto-renamed: moving a person is `rename_user`, which knows all 47 attribution columns and the private schema, which only services/private_notes.py names. Operator config never aborts boot — a name it cannot reserve is a logged error, the way a bad model provider degrades to mock | `services/users.py` · `routes/deps.py` · `main.py` perimeter |
| Rate caps | per-user sliding window on flood-prone writes: capture 30/min (REST, chat, and MCP), ingest 6/min, key requests 3/min, and task delegation, question assignment and the chat thread and folder writes on the shared `write`/`delete` buckets — question assignment because it NOTIFIES the assignee, so it is a send rather than an edit. The `/api/private/*` writes take a bucket of their OWN: that store is excluded from portable export, FTS, and every agent surface, so nothing else would notice a flood, and sharing the write budget would lock a person out of their 1:1 notes during a busy planning hour. Which routes may go uncapped is a TEST, not a habit: `tests/test_bounded_routes.py` walks the route table and fails any mutating route that neither calls the check nor carries an EXEMPT row with a reason, and fails an EXEMPT row that stopped being true. A DoS-annoyance guard, not a security control. A spent cap answers **429** with a `Retry-After` computed from the window, never a bare 400, so a client can tell throttling from a malformed body and knows when to retry. The `write` bucket keys on the (agent, requester) PAIR, so the shared default chat identity is not one team-wide budget | `app/ratelimit.py` |

### Activity-ledger claim boundaries

The chain protects the stored fields of recorded activity rows. Each digest
covers `seq`, `created_at`, `actor`, `action`, `detail`, and the previous
digest. It does not cover `activity.id`, domain rows, or artifact files. The
append transaction writes the live sequence and digest with each chained row.
A direct chained insert or a truncation leaves a mark contradiction. A full
verification reads one repeatable snapshot. It walks the digest links unless
an earlier row-shape or mark fault stops it.

Unchained rows have no digest protection. The verifier compares their count
with the migration baseline. This detects a count change while the in-database
mark stays honest. The anchor log accepts a lower baseline only after a chained
adoption receipt and a later anchor record it. The nightly job adopts these
rows under the chain lock. Adoption protects current content, but it does not
prove the original source or time.

The verified anchor records the newest suffix that a scheduled run examined.
The anchor log copies that sequence and digest to independent files. These
files are unsigned. Their value comes from storage that a database writer
cannot change. The local file is the only external record without a mirror.
An attacker with write access to the database and all anchor files can replace
the history without detection.

The chain uses an unkeyed digest. A database writer can recompute rows and the
in-database marks. An earlier anchor can expose that rewrite if its file stays
trustworthy. The chain proves integrity of recorded fields within this trust
boundary. It does not prove that every effect produced a row. It also does not
prove the actor name, especially in trusted-header mode.

Database writes inside `db.transaction()` commit with their queued activity
rows. A failed chain append rolls back that transaction. Standalone log calls
use an unchained fallback after a chained append failure. Artifact files follow
the transaction through `services/artifact_files.py`: new bytes become durable
before the row can commit, a rollback removes the new file and keeps the old
one, and a replaced revision is deleted only after commit. A hard process crash
can leave an unreferenced file. It cannot leave a committed row that points at
partial bytes. Other filesystem and network effects stay outside the database
transaction, so the ledger is not a complete transaction journal for them.

An artifact content digest is an unkeyed value in the same database row as its
path. It detects disagreement between that row and the file before Skein
parses, returns, or otherwise uses the bytes. It does not extend the activity chain over artifact files. An actor
who can rewrite the row and the file can replace both values without detection.

The four settings that hold a whole document — `SKEIN_MODELS`,
`SKEIN_MODEL_PRICES`, `SKEIN_MODEL_PARAMS`, `SKEIN_MCP_SERVERS` — each also
take a `<NAME>_FILE` path and read the same value from a mounted YAML file,
which carries the comments and nesting a one-line JSON value cannot. The file
is re-encoded to JSON before the same parser reads it, so shape rules and
fault wording are identical either way (`config._structured`,
`tests/test_config_files.py`). Setting both forms of one setting is a fault:
the one you were not looking at would otherwise win in silence. A fault names
the variable and, for a YAML error, the line — never the path and never the
text, because these strings reach every signed-in user.
